LEAD INTELLIGENCE PROJECT - PROJECT NOTES
Updated: 10 November 2026

WHAT THE PROJECT IS ABOUT
This prototype helps screen-printing shops find organizations that may need branded workwear. It searches for buying signals, presents the evidence for review, and helps identify the right company and operational contacts. Construction contractors in the Dallas-Fort Worth area are the initial pilot; the intended system can later support other industries and signals.

MAJOR UPDATES
- Company discovery: Search the web with selected buying-signal queries, including a 15-query construction pilot and a larger experimental query bank. Users can select up to ten queries per search.
- Classification: GPT-4o mini reviews stored search-result details. The dashboard scores and sorts results and lets a screen printer record a call/skip review.
- Source research: A curated monitor list focuses on project trackers, public records and construction publications, rather than individual contractor websites.
- Contractor verification: Eligible project leads use existing evidence and ranked searches for awards, permits, first-party reports and trade coverage. The system distinguishes a developer from a general contractor and pending awards from confirmed roles. A second AI review checks cited evidence for new confirmations.
- Contact lookup: A configured Apify Actor searches for operational contacts, followed by GPT-4o mini role-suitability review. This does not independently verify a person's current employment or email.
- User experience: Source links, alternative links, progress and error messages are available in the dashboard. Search setup supports background updates without losing matching query selections.
- Duplicate handling: Exact duplicate source pages can be grouped and an existing verification reused. This does not guarantee all different articles about the same project are deduplicated.

INDEPENDENT AGENT DEMO
An independent research demo examined 14 unresolved result rows representing 12 distinct investigations. It found three confirmed contractors (25% of 12), one probable candidate, five unresolved cases and three unsuitable leads. One confirmed project was in Guam and one had already been confirmed elsewhere in the database; only one was a new confirmed Texas discovery. The number of individual search queries was not recorded, so a per-query success rate is unavailable. This was a small exploratory test, not a comparison against the dashboard on the same leads.

KNOWN LIMITATIONS AND NEXT STEPS
- Existing AI classifications and historical contractor confirmations need human review; a developer or a pending award must not be presented as a confirmed general contractor without project-specific evidence.
- Test the automated contractor lookup against the same projects as the independent agent, track evidence and costs, and address errors in confidence/status handling.
- Validate the configured Apify contact workflow end-to-end with a live run. Provider records, company matches, roles and email deliverability require independent checks. The carefully filtered manual test is not necessarily the same as the app's current request.
- Expand research and prompt configuration for other industries after the construction pilot is validated.
- The dashboard is a local prototype, not a deployed product. Runtime API keys are entered locally and the local lead database is not included in Git.

DETAILED HANDOFF: PRODUCT AND USER REQUIREMENTS
The customer is a screen-printing shop looking for organizations likely to need branded clothing.
A buying signal is a public event that may indicate demand, not proof of a purchase. Initial signals
are contract awards, project starts, expansion and hiring. Construction and DFW are the pilot,
not the permanent product boundary. Future categories may include schools, restaurants or others;
their signals, target roles and prompts will need separate research and configuration.

The user wants the system to discover companies from public sources. An earlier version presented
a list of known companies to check, which did not meet this requirement. The current discovery
workflow starts from search queries instead. Monitoring preselected publications and government
sources is a separate supporting workflow. The desired end result is a usable, sourced lead and,
where possible, the right operational contact, not simply a long list of websites.

The user values concise cards, clickable source headings, a small title-and-domain hover preview,
alternative links, accurate progress and clear provider-specific errors. Long operations should
show status in place without interrupting scrolling or reloading the page. A source link or an
AI score is a starting point for review; it is not an independently verified sales opportunity.

LANGUAGES, STORAGE AND EXECUTION
Python 3.11+ is the primary implementation language. The standard library provides the local HTTP
server, request handling, JSON, networking and SQLite integration; the core prototype does not
require an application framework. SQL defines and queries SQLite tables, including an FTS5 evidence
index. SQLite stores discovery runs, source evidence, classification, reviews, provider accounting
and enrichment history. HTML, CSS and browser JavaScript are generated/served by the Python UI
modules; JavaScript handles interactive controls and background requests. JSON stores structured
configuration, query data, provider payloads and selected research catalogues. Markdown and this
text file hold human-readable documentation. Tests use Python's unittest framework and mock
provider transports. The app is local and binds to 127.0.0.1; it is not a hosted service.

DISCOVERY AND QUERY APPROACH
The user found the initial two searches too narrow and asked for 10-20 targeted queries and the
ability to select up to ten in one run. The app now offers a 15-term pilot set plus a larger
experimental bank. Templates vary by trade, signal and geography; the recommended terms favor
awards, project starts and expansion, with some hiring searches. Query preview itself is free;
each selected Tavily Basic search can consume a provider credit. Local daily/monthly limits do not
represent usage made elsewhere in the user's Tavily account.

The top-15 ranking was informed by a DFW pilot and independent public search, but all 15 were not
tested in one controlled simultaneous experiment. Search effectiveness can change by geography,
provider and date. Measure usable, verified companies per credit rather than raw result volume.
Search terms for discovering buying signals are in query_bank.py. Separate contractor verification
queries are in contractor_verification.py; the two sets serve different steps.

CLASSIFICATION AND SALES REVIEW
Initial classification uses GPT-4o mini on stored title, snippet, URL, originating query and
available date, rather than automatically reading the entire destination page. It returns
structured fields for company, signal, evidence and explanation. Application code calculates a
score, applies eligibility checks and retains the old regex output for historical comparison.
The classification page presents higher scores first and allows Would call / Would not call /
Unsure reviews. Classification progress must distinguish the current batch from all stored results.

Earlier results exposed limits: an unrelated caregiver vacancy, a single safety-manager vacancy
mistaken for bulk hiring, and generic phrases treated as business names. Scores and structured
output can still be wrong. Recheck the evidence, company identity, role, timing and geography.
The system is not yet validated across other industries.

PROJECT-CONTRACTOR LOOKUP AND WHY IT CHANGED
For a project-start or contract-award lead, the company in a headline may be the owner or developer
rather than the construction contractor. The user specifically challenged an incorrect Trademark
Property Co. finding on Dunham Pointe. That stored finding was changed to unresolved; the original
finding was preserved in its record. A proposed award or upcoming council vote is also not proof
of a final award. The Pat Hallisey Park example initially exposed that error.

The current ranked method first reuses an exact-page verification and existing lead/Apify evidence.
For award signals it searches for final official awards, bid/meeting decisions and permits before
secondary reports. For project starts it prioritizes permits, owner/developer announcements and
planning records, then trade reports and broad search. These are targeted Tavily web searches,
not dedicated direct integrations to every named government database. A fully unresolved run can
use up to five Basic searches; existing evidence or a confirmed result can stop it earlier.

GPT-4o mini assesses whether evidence establishes a named project and the contractor's actual role,
and distinguishes confirmed, pending, likely and unresolved. Code validates structured output
and cited URLs. A second model review checks new confirmations against cited evidence; this is
another automated check, not independent proof. Historical confirmations were not all re-audited.
One known error occurred when status and confidence were inconsistent: 'Pending or likely contractor
status requires probable confidence'. Handle/retest that case rather than treating it as a finding.
Exact source-page duplicates can reuse a lookup; different pages about the same project may not.

Examples from independent agent research: LMF Construction was named for Hall Park Terra Residences;
SpawGlass had an official approval record for Pat Hallisey Park (already present elsewhere in the
database); MYCON was a candidate for Denton Enterprise Logistics Park but the reviewed evidence
did not explicitly establish its contractor role. These examples illustrate why project identity,
role, finality, geography and source access must be checked. The agent demo was exploratory; no
matched comparison with the automated method has been run, and its exact query count was not logged.

APIFY: TWO DISTINCT USES
Website evidence enrichment retrieves bounded source pages for an eligible lead. It is separate
from finding employee contacts and does not itself prove a contractor's role. Contact enrichment
uses the configured pipelinelabs lead-scraper Actor to look for people at the target company.
The implemented construction role profile focuses on project, operations and construction managers;
principal titles are excluded. Requests are capped at five results and a $0.10 Actor charge.
The model reviews returned role suitability; it does not conduct independent background research
or establish that email addresses are deliverable or employment is current.

The previous employee Actor encountered a free-user run limit that could appear as a successful
run with zero results. Other runs produced zero contacts or records the parser could not read.
The newer integration checks run status and reports provider errors where available. A manual
Trademark test used strict company-domain and other filters; do not assume those manual filters
are all wired into the app. The live end-to-end contact workflow and returned identity/domain
quality still need verification before relying on it. Avoid unnecessary paid retries; inspect
the Actor run ID, submitted input, status and output first. Do not put API keys in docs, source,
logs or Git. Apify and OpenAI have separate credentials, limits and charges.

MONITOR SOURCES AND EVIDENCE
The source catalogue emphasizes direct pages for construction projects, openings and contract
decisions rather than contractors' company homepages. City procurement listings may be solicitations,
not final awards; bidders and low bidders are not automatically the winner. Public meeting decisions,
award notices and issued permits can be stronger evidence if they identify the same project and
contractor. Private-project announcements and trade reports can help, but must state the role.
Some sources require accounts, have incomplete coverage or cannot be crawled reliably. A search
result or an alternative-link fallback does not guarantee source access.
